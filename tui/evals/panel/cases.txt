# The write prompt's evaluation cases (#410), read by tui/examples/panel_eval.rs.
#
# === <id>, then:
#   kind:    bug, feature, investigate, plan, refactor, review, research, message, command, ops, hint, format
#   window:  name · cmd · path, as the panel captures them
#   out:     the output type picked in the panel (default auto)
#   out_is:  for write or either, a reply that is not a question must be this type
#            (prompt, steps, command, text, format or hint); auto is not one
#   expect:  ask    - the right first move is a question
#            write  - the input settles it: no question
#            either - an on-target question, or a reply with every must, both serve
#   ask_any: for ask or either, the question or one option names one of these (; separated, any case)
#   must:    for write or either, the reply carries every one of these
#   must_not: the reply, a question included, carries none of these
#   holdout: yes for a case written after the prompt it is run on (default no)
# Words match whole and in any case ("plan" is not in "explanation"); "a|b" is
# any of them. A must_not cannot tell "no subagent" from "a subagent".
# A key or a section given twice is an error. A screen cannot hold a line that
# starts with "--- " or "=== ": those start a section or a case.
#   note:    why the label is what it is
# then "--- screen" (optional), "--- repo" (optional), "--- conversation" (optional),
# "--- refs" (optional) and "--- request".
# A refs body is the prompt basket (#365 child 5), one "path", "path:a" or
# "path:a-b" line a ref, from the pane's folder; "../x" is a file outside it. The
# case then runs in a temp folder of its own that holds those files, named as the
# window's path ends; an explore case's refs inside its fixture must exist there.
# A conversation body is the panel's earlier rounds, one "assistant: <question>
# Options: a | b" or "user: <answer>" line each, oldest first: the case is then
# its next call, with one question fewer left for each one asked.
# A repo body is the <repo> block the panel sends for a window in a git repo
# (capture.rs repo_state): branch, root, status, recent commits, diff --stat and the
# screen's paths, each section's lines indented by two.
#
# Label rule (#503): ask when the possible readings lead to different work, or
# when the reply would otherwise guess something only the owner knows: their
# intent, the scope, the goal of a plan or refactor, what a review should weigh
# most, the kind and fields of generated config, a fact outside the repo. A
# guess written down as an "Assumed:" line is still a guess: such a case is ask.
# A fact the agent can find (by reading files, running a command) is never a
# reason to ask; the prompt tells the agent to check it and handle each case.
# A vague feature may still go plan-first (#451): either. Cases here are not the
# prompt's own examples on purpose. A case relabelled by #503 says so in note.
#
# Big tasks (#558): a big feature, a migration or a refactor across many files
# gets the facts first. The prompt has the agent read the current flow and run
# the tests or the tool for a baseline, plan, wait for the OK, then run the same
# checks again and compare. For a big feature, the panel asks only the one or two
# points that change the work most; the prompt has the agent interview the owner
# for the rest with its question tool and get an OK on a requirements list
# before the plan. A small addition to existing code checks that what exists
# works, adds, then tests both. A trivial edit gets none of this. A prompt that
# reports and lists the edits for the owner's approval answers "should we move
# to X" (#514). The prompt asks for no installed skill: the agent picks one from
# its description (#513). A case relabelled by #558 says so in note.
