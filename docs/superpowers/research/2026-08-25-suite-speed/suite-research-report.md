# Fast/reliable bash+tmux integration test suites — research report

Context: one 5900-line bash file, 115 blocks, each spinning a private tmux server
(`tmux -L sock -f /dev/null new-session -d`), driven via `send-keys`/`capture-pane`,
synced with ~97s of fixed `sleep` in a ~180s run. 12-core box. Separate "freeze rig"
parses `tmux -vv` logs for redraw cost.

## DO

1. Give every parallel worker/shard its own private tmux socket (`-L`/`-S`), never share
   one server across concurrent tests. [E] libtmux's `TestServer` pytest fixture exists
   specifically to hand each test/worker "servers with unique socket names" that
   self-cleanup — https://libtmux.git-pull.com/pytest-plugin/ (fetched; content behind a
   redirect page but corroborated via search index) and
   https://github.com/tmux-python/libtmux/pull/439.
2. Shard/parallelize at the *file* (block) granularity, not inside a file, when blocks
   share any state. [E] bats-core: "Ordering of parallelised tests is not guaranteed...
   may break suites with dependencies between tests (or tests that write to shared
   locations)" and `--no-parallelize-across-files` trades some parallelism for
   deterministic per-file output —
   https://github.com/bats-core/bats-core/blob/master/docs/source/usage.md (fetched,
   lines 92-111).
3. Poll for a condition with a deadline instead of sleeping a fixed duration. [E] general
   flaky-test literature: "Fixed sleeps are bad because they wait for time, not for
   truth... Replace fixed sleeps with explicit wait-for conditions (poll with timeout)" —
   https://www.getpanto.ai/blog/common-test-failure-patterns ;
   https://github.com/fabric8io/kubernetes-client/issues/7391 (Thread.sleep → Awaitility).
4. Use `tmux wait-for` as tmux's *native* blocking primitive instead of polling from the
   outside when the thing you're waiting on can itself signal a channel. [E] tmux(1) man
   page (fetched from github.com/tmux/tmux/master/tmux.1, lines 8801-8850): "When used
   without options, prevents the client from exiting until woken using `wait-for -S` with
   the same channel... With `-E`, tmux waits for the next event with `name`. Events
   include hook and notification names, and user `@` events generated by `set-hook -E` or
   `set-hook -B`." `-L` locks a channel so other waiters block until `-U` unlocks it.
5. Re-run any newly-parallelized suite several times before trusting it, since ordering
   and hidden shared-state bugs mostly hide until parallel. [E] bats-core docs: "When
   enabling `--jobs` for the first time be sure to re-run bats multiple times to identify
   any inter-test dependencies or non-deterministic test behaviour" (same URL as #2).

## DON'T

1. Don't synchronize with fixed sleeps sized for the dev machine — they either waste time
   or flake under CI/parallel load. [E] "A test that's reliable on the dev's laptop with
   no other load will fail on a CI runner that's also building three other apps in
   parallel" — https://www.getpanto.ai/blog/common-test-failure-patterns. [I] Directly
   applicable to your ~97s of sleeps: 12 cores running shards concurrently will contend
   for CPU in a way a serial run never does, so sleep durations calibrated serially are
   not safe once parallelized.
2. Don't assume tests are safe to run outside an isolated environment once they touch
   real tmux/shell state. [E] tmux-plugins/tmux-test's own `run_tests_in_isolation`
   entrypoint carries the comment: "This script should be run within an isolated
   enviroment (Vagrant, travis). Depending on what the tests do, it might NOT be safe to
   run this script directly on the development machine." —
   https://github.com/tmux-plugins/tmux-test/blob/master/tests/run_tests_in_isolation
   (fetched). Their own runner is a plain serial `for test_file in ...` loop — no
   parallelism at all.
3. Don't rely on a shared/default tmux server or shared `~/.tmux.conf`/`~/.tmux/` across
   test invocations. [E] tmux-resurrect's `teardown_helper` unconditionally does
   `rm -f ~/.tmux.conf; rm -rf ~/.tmux/; tmux kill-server` between tests —
   https://github.com/tmux-plugins/tmux-resurrect/blob/master/tests/helpers/helpers.sh
   (fetched) — i.e. even a mature, widely-used plugin's suite mutates real dotfiles and
   the default socket, which is exactly why it must run serially/isolated and is not
   parallel-safe as written. Don't copy this pattern; use private `-L`/`-S` sockets and
   `-f /dev/null` (which your suite already does) instead of touching `$HOME`.
4. Don't assume `/tmp` socket-dir cleanup races are harmless when many private sockets
   are created/destroyed concurrently. [I] No direct tmux-specific citation found for
   this exact claim; inferred from the general port/socket-collision literature: a
   PostgreSQL parallel-test thread describes TOCTOU races when workers pick "free"
   ports/sockets concurrently, fixed by assigning each worker an *exclusive* range/name
   up front rather than probing for availability —
   https://www.postgresql.org/message-id/19122.1357235881@sss.pgh.pa.us. Applied to tmux:
   derive each shard's socket name deterministically from its shard/worker id (e.g.
   `cockpit-test-$$-$SHARD`), don't let two shards race to create-then-check a socket
   path.
5. Don't leave timing-sensitive assertions (redraw cost, latency budgets) mixed into the
   same parallel run as functional tests — they need a serial, low-noise lane. [I]
   Composite inference from (a) bats-core's own advice to isolate interfering tests via
   `--no-parallelize-within-files` / `BATS_NO_PARALLELIZE_WITHIN_FILE`
   (bats-core usage.md, lines 108-111, fetched) and (b) the general flaky-test guidance
   that CPU-contended CI runners break fixed-time assertions. No source explicitly
   discusses tmux redraw-perf tests under parallel load — treat this line as [I] throughout.

## 1. Parallel runners for shell test suites

- **bats-core `--jobs`** (fetched `docs/source/usage.md`, lines 91-111): needs GNU
  parallel or a compatible replacement; unordered by default so it "may break suites
  with dependencies between tests (or tests that write to shared locations)";
  `--no-parallelize-across-files` parallelizes only within a file, running files
  sequentially, trading throughput for deterministic/immediate output;
  `--no-parallelize-within-files` (or `BATS_NO_PARALLELIZE_WITHIN_FILE=true` set in
  `setup_file()`) opts a single file out of internal parallelism. [E]
- Known GNU-parallel-related friction: bats-core issue #1182 requests a per-test
  opt-out of parallel execution for tests that must run exclusively (e.g. tests that
  themselves spawn parallel workloads and would collide with sibling test parallelism);
  issue #290 reports an "odd failure when using --jobs." [E, titles only — not fetched
  in full, so treat specifics as [I]] — https://github.com/bats-core/bats-core/issues/1182,
  https://github.com/bats-core/bats-core/issues/290.
- **ShellSpec `--jobs`**: parallel jobs are dispatched per specfile — "It is necessary to
  separate the specfile for effective parallel execution" — and the framework warns
  "Tested scripts should be stateless or properly isolated to avoid race conditions"; the
  streaming reporter can print a file's failure location out of the actual stop order
  since specfiles run concurrently. [E]
  https://github.com/shellspec/shellspec/blob/master/docs/cli.md (search-index summary;
  not directly fetched, so treat exact wording as paraphrase-level [E] via search
  snippet).
- **Plain `xargs -P` / `make -j` sharding**: standard pattern is `xargs -P<n> -n1` to fan
  out N independent shard invocations; merging is manual (each shard writes its own
  log/exit code to a file, a wrapper aggregates). [I] general knowledge, not
  suite-specific — no single canonical citation found beyond generic xargs tutorials
  (https://blog.tratif.com/2023/01/30/bash-tips-5-parallelism-using-xargs/).
- **shunit2**: no evidence found of any built-in parallel mode; not covered further.

## 2. Synchronizing with tmux without sleeping

- **`tmux wait-for`** (fetched tmux.1 source, lines 8801-8850, quoted above under DO #4):
  three real primitives — (a) plain `wait-for name` blocks until `wait-for -S name`
  fires the same channel (rendezvous/semaphore); (b) `wait-for -L name` takes a lock,
  other clients calling `-L` on the same name block until `-U` unlocks it (mutex); (c)
  `wait-for -E name` blocks until a hook/notification/user `@`-event named `name` fires,
  which is the piece that lets a test block on a real tmux-side event (e.g. a hook set
  with `set-hook -g` on `pane-mode-changed`, `window-resized`, etc.) instead of polling
  `capture-pane` in a loop. This is the most directly transferable primitive for
  sleep-free sync in a private-per-test tmux server. [E]
- **`tmux -C` control mode**: man page snippet found via search — "-C flag starts a
  client in control mode... intended for testing" — control mode streams `%output`,
  `%layout-change`, etc. as they happen, so a driver can block on a read() instead of
  guessing a delay. [E] https://github.com/tmux/tmux/wiki/Control-Mode (search snippet,
  not fully fetched — treat exact quote as [I]-adjacent).
- **Format-variable polling** (`#{pane_current_command}`, `#{session_attached}`,
  `#{client_width}`): confirmed these format keys exist and are documented in tmux.1
  (fetched, lines 7295, 7394, 7467 respectively: `client_width` = "Width of client",
  `pane_current_command` = "Current command if available", `session_attached` = "Number
  of clients session is attached to"). [E] Using these means polling
  `tmux display-message -p '#{pane_current_command}'` in a tight loop with a deadline —
  still a poll, but polling a cheap synchronous tmux query is far lighter and more
  precise than sleeping then blind-`capture-pane`-ing.
- **tmux's own `regress/` directory**: could not locate/fetch a `regress/` directory in
  the current tmux/tmux repo via search or the files browsed (the man page tree was
  fetched directly; a dedicated regression-test directory was not found in this pass).
  [I — unresolved]. Do not cite tmux's own regression harness as a model; not verified.
- **tmux-plugins/tmux-test** (the framework underlying tmux-resurrect/tmux-continuum/tpm
  tests): fetched `tests/helpers/helpers.sh` and `tests/run_tests_in_isolation` directly.
  Findings: no `wait-for`, no control-mode, no format-variable polling anywhere in the
  helper layer — synchronization is 100% fixed `sleep` (see tmux-resurrect's
  `expect_helpers.exp`, fetched: `sleep 0.2` after most keystrokes, `sleep 1`/`sleep 5`/
  `sleep 10` after triggering save/restore). Tests run **serially**, one `for` loop, no
  parallelism, and the runner explicitly says it may be unsafe outside an isolated VM
  because it mutates `~/.tmux.conf` and `~/.tmux/`. [E] — this is a *counter-example*,
  not a technique to copy; it shows what the ecosystem's most-used plugin test harness
  actually does (sleep+serial+global-state), which is weaker than what your suite
  already does (private sockets via `-L`).
- **libtmux pytest plugin / `TestServer` fixture**: search-index evidence (page fetch was
  blocked by a client-side redirect) says the plugin "automatically manages setup and
  teardown of an independent tmux server" per test, and a `TestServer` factory fixture
  "creates servers with unique socket names" for tests needing multiple servers, each
  auto-cleaned at test end. [E, via search snippet — direct page fetch failed, so
  treat exact wording as paraphrase] https://libtmux.git-pull.com/pytest-plugin/. No
  confirmed evidence found on whether libtmux's own suite runs under `pytest-xdist`
  (parallel) — unresolved, mark [I] if assumed.
- **tmuxp tests**: not investigated this pass — out of budget, not covered.

## 3. What NOT to do

- **Fixed sleeps as sync**: general flaky-test literature converges on "wait on a
  condition, not a clock" — https://www.getpanto.ai/blog/common-test-failure-patterns;
  https://github.com/fabric8io/kubernetes-client/issues/7391 (`Thread.sleep` →
  `Awaitility`, explicitly filed as a flakiness-prevention issue). [E]
- **Sharing one tmux server across parallel tests**: not directly documented as a
  named anti-pattern in any fetched source, but strongly implied by (a) tmux-test's own
  warning about running outside isolation because tests mutate shared `~/.tmux.conf` /
  the default socket (fetched, cited above) and (b) libtmux's `TestServer` fixture
  existing specifically to give each test a private socket (search snippet). [I]
  synthesized from both.
- **`pkill -f` patterns**: no direct citation found this pass for tmux-specific guidance
  against `pkill -f tmux`; general risk (killing unrelated processes matching the
  pattern) is common knowledge, not independently sourced here — mark [I], unresolved
  citation.
- **Timing assertions on a loaded machine**: bats-core's `--no-parallelize-within-files`
  / `BATS_NO_PARALLELIZE_WITHIN_FILE` exists precisely so interference-prone tests (their
  own example: MPI/OpenMP/CUDA workloads per bats-core issue discussion) can opt out of
  parallel execution rather than get flaky timing failures — fetched usage.md, lines
  108-111, and bats-core issue #998 (title only, "tests need to know if they're running
  in parallel," not fetched in full). [E for the opt-out mechanism, I for generalizing it
  to "perf tests need a serial/isolated lane"].
- **Reading sleep-settled screens vs. waiting for a prompt marker**: not independently
  sourced this pass beyond the general "poll for truth not time" literature already
  cited under DON'T #1. [I]
- **Relying on `/tmp` socket-dir inode cleanup**: not tmux-specific; inferred from the
  PostgreSQL parallel-test port-collision thread (cited above, DON'T #4). [I]

## 4. Measuring tmux redraw/CPU cost deterministically

- **`tmux -v` / `-vv` logging** (fetched tmux.1, lines 229-252): `-v` "Request verbose
  logging. Log messages will be saved into `tmux-client-PID.log` and
  `tmux-server-PID.log` files in the current directory." A second `-v` (i.e. `-vv`) adds
  "an additional `tmux-out-PID.log` file... generated with a copy of everything tmux
  writes to the terminal" — i.e. `-vv` captures the actual terminal output stream tmux
  produced, which is what a redraw-cost rig would diff/measure against. `SIGUSR2` to the
  server toggles this logging on/off at runtime without restarting the server. [E]
- No fetched source documents `server_status_*` or a `pane loop:` log-line format
  specifically — these were not found/verified in this pass against the tmux.1 source or
  search results. [I — unresolved]. If your freeze rig already parses these lines
  successfully against real `-vv` output, that's stronger ground truth than anything
  found here; this report can't independently confirm the log-line schema from docs
  alone (it isn't documented in tmux.1 — it would have to come from reading
  `screen-redraw.c`/`tty.c` source, which fetched partially at
  https://github.com/tmux/tmux/blob/master/screen-redraw.c but wasn't grepped for log
  format strings this pass).
- No nicm issue/discussion was found this pass that gives an explicit "how to benchmark
  tmux" methodology recommendation; the closest hits (#5419 "Synchronized client redraw
  toggles an otherwise-visible cursor," #5298 fzf redraw/input lag) are bug reports where
  `-vv` logs were the requested diagnostic artifact, not a documented benchmarking
  procedure. [I] Treat "capture `-vv` logs and diff the emitted escape sequences /
  civis-cnorm pairs" as the de facto convention inferred from how maintainers debug these
  issues, not as a stated methodology.

## Three most transferable techniques for this exact shape (one bash file, 115 private-socket blocks)

1. **Shard by block across N private-socket workers with `xargs -P$(nproc)`,
   deterministic socket names.** Split the 115 blocks into shard groups (e.g. by
   line-range or a block-id list), invoke each shard as `bash suite.sh --blocks=<ids>
   --socket=cockpit-test-$SHARD` via `xargs -P12 -n1`, each shard writes
   `results/$SHARD.tap` (or exit code) to a file; a final step concatenates and sums exit
   codes. This mirrors bats-core's `--jobs`/file-level model (parallelize across
   independent units, not within one) [E, bats-core usage.md] and avoids the socket-race
   risk by having each shard *own* its socket name rather than probe for a free one
   [I, inferred from Postgres port-collision thread].
2. **Replace `sleep N; capture-pane` with a poll-with-deadline on a cheap tmux query,
   and use `wait-for -E`/hooks for anything tmux can signal.** For "did the pane finish
   redrawing/settle," poll `tmux -L $sock display-message -p '#{pane_current_command}'`
   (or `#{client_width}`/`#{session_attached}` where relevant) in a tight loop with a
   short interval and a hard deadline, instead of a flat sleep — this collapses your 97s
   of dead time into "however long the real work took, plus one poll interval," and
   removes the CI/parallel-load flakiness fixed sleeps are known for [E, tmux.1 format
   variables + general flaky-test literature]. Where a test is waiting on a specific tmux
   event (window resize, mode change) rather than a shell prompt, `wait-for -E` lets tmux
   push the wakeup instead of your script pulling for it [E, tmux.1 wait-for section].
3. **Pull timing/perf assertions (the freeze rig's redraw-cost checks) into their own
   serial, unsharded lane, run after the parallel functional shards.** This is bats-core's
   own answer to "some tests interfere with / are sensitive to concurrent execution":
   `--no-parallelize-within-files` / opting a group out entirely [E, bats-core usage.md].
   For your suite: keep the 115 functional blocks parallel-shardable, but run the `-vv`
   log-based redraw measurement as a dedicated non-parallel pass (or on a pinned subset
   of cores) so its timing numbers aren't contaminated by 11 sibling shards competing for
   CPU — a real risk your 12-core box will hit the moment shards go concurrent
   [I, synthesized from bats-core's opt-out mechanism + general CI-load flakiness
   literature; no tmux-specific source confirms this exact risk for redraw timing].
